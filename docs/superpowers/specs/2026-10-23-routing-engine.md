# Standalone route calculator: up to two transfers

Date: 2026-10-23. Authorized implementation; preserve existing uncommitted work. No dependencies, commits, deployment, AI parser, agent, RAG integration, or API key.

## Outcome

Both ordinary journey planning and each adjacent pair in the multi-destination tab use one deterministic calculator. It finds directed journeys using one, two, or three vehicles, accounts for access, every interchange walk, and egress, and describes data limitations honestly. The result remains a reusable structured tool independent of AI.

## Evidence and data boundary

- `public/data/routes_summary.v2.json` has 1,794 directional entries: 1,784 road trips and 10 manual metro directions. Road `route.id` equals GTFS `trip_id`; `route_id` alone cannot select a direction.
- `artifacts/data-audit/gtfs-ordered-road-stops.json` contains 1,784 entries `{trip_id,route_id,direction_id,shape_id,headsign,ordered_stops:[{id,name_en,translations,lat,lng}]}`. This preserves order, but omits permissions and sequence numbers. Read the local ZIP to construct the production data.
- ZIP `stop_times.txt` currently has `trip_id,stop_id,stop_sequence,arrival_time,departure_time`; routes have `continuous_pickup,continuous_drop_off`. Preserve optional pickup/drop-off fields if encountered and apply GTFS defaults when absent. The current feed has 44,743 stop calls and no transfers.txt; no interchange has source-verified transfer permission. Continuous pickup permission does not establish safe roadside boarding; use listed calls only in this version.
- Road `via_stops` is generated by proximity and capped at 30; never use it to infer road membership or order. Manual metro `via_stops` is a deliberately ordered station list. Join each metro name exactly to a public `type:'metro'` station after stripping the display prefix, constrained by `stop.lines` containing `route.num`. Ambiguous/missing matches are reported, never guessed. Keep branch-specific lists and direction.
- Feed calendars end 2025-12-31. This is historical source evidence, not verification that services operate today. Existing metro is manual data, also unverified. Do not route by expired timetable times or advertise departures/live availability.

## Network and search

Build a versioned static `public/data/routing_network.v1.json` with metadata, deduplicated stops and ordered per-trip calls. Each call retains stop ID, sequence, boarding/alighting permission and cumulative estimated ride distance; each trip retains source and app direction ID. Use source shapes for monotonic distance projection where reliable; otherwise use summed successive stop distances and flag that estimate. Never reorder calls by projection. Reject malformed identities/coordinates and report coverage. Do not silently omit an unmatched route or replace it with polyline-based boarding.

Load once per JS context through a shared promise that resets after failure. Build stop spatial buckets, stop-to-trip-call indexes, and directed route scans once, cache by dataset object/version. Avoid all-pairs route combinations. Search at most three boarding rounds with positive estimated costs, parent pointers and safe dominance at the same state/round. State must retain any history affecting permitted next moves. All reachable candidate trips and calls participate; no first-five truncation, no hardcoded transfer hubs, no skipping transfers when direct results exist. Apply vehicle filter before searching and before final result limiting. Microbus filter includes Microbus, Box and Tomnaya.

Access and egress walking each default to 1,200 m; each transfer walk defaults to 600 m; total walking must not exceed maxTotalWalkMeters (default 3,600 m). Nearby distinct stops connect through the spatial index, using their actual individual coordinates; geometric route crossings never create boarding or transfer points. Use one walking edge per interchange, without chaining arbitrary walks to evade the limit. Shared stop IDs allow interchange; nearby distinct IDs yield explicitly estimated interchange walks. Initial walking cost is straight-line distance / 80 m per minute and is explicitly unverified for street access. All ride times use a documented estimate of 3 minutes per km; use a separate 5-minute transfer penalty for ranking only. Display travel duration excludes this ranking penalty and visibly states waiting time is unknown. Zero distance yields zero walk time. No actual timetable/wait-time claim.

Rank deterministically by total estimated minutes, total walking, transfer count, stable identity. Keep up to 15 direct and 8 transfer results after search/deduplication. Output stable IDs include every ride trip ID and boarding/alighting call sequence, not merely a route pair or a hub. Zero-distance endpoints return empty results with `status:'same-point'`; invalid/no nearby/no connected service return explicit empty statuses. Missing network loading is a data error with retry, not 'no route exists'.

## Shared result contract and UI

`planJourney(origin, destination, network, {maxWalkMeters=1200,maxTransferWalkMeters=600,maxTotalWalkMeters=3600,maxTransfers=2,vehicle='ALL'}={})` returns `{status,directRoutes,transferRoutes,metadata}`. Preserve the two grouping arrays to minimize outer UI churn, but migrate every consumer away from fixed `leg1`/`leg2`/`hub` assumptions. No parallel legacy journey representation.

Every journey has `{id,type,legs,transfers,totalWalkMeters,totalRideKm,totalTimeMinutes,estimated:true,warnings}`. `type` is `direct` or `transfer`; `transfers` is ride count minus one. `legs` alternates `{kind:'walk',fromCoord,toCoord,distanceMeters,durationMinutes,verification:'estimated',purpose:'access'|'transfer'|'egress'}` and `{kind:'ride',route,tripId,fromStop,toStop,fromSequence,toSequence,fromCoord,toCoord,distanceMeters,durationMinutes,path,source}`. Include zero-length boundary walks consistently. Ride path is produced lazily for selected journeys to avoid geometry work in every search, and follows the direction between calls; do not draw the whole line as a journey leg. When geometry projection is uncertain, display the estimated stop-chain path honestly.

Both tabs display all rides and walk segments, 0/1/2 transfers, vehicle type plus line number/name, boarding/alighting station names, walking totals, estimated minutes, and a visible historical/unverified service-data notice. Walks visibly say approximate and street accessibility unverified; do not call them verified or safe. Existing `walkRoute` may refine a selected walk, but is not required for this first delivery and must not silently change search totals or remove the uncertainty claim. No claimed real-world operation, officialness, or live data.

Map iterates arbitrary `legs` with ride colors and walk dashes and fits the actual journey. Avoid duplicate full selected-route overlays for active journeys. Ordinary selection, worker relinking and multi-stop selection/filter/cache use the same stable journey IDs and all ride routes. Invalidate multi-stop cache when vehicle/options/network version changes; stale async replies must not overwrite newer inputs. Existing tracking is single-vehicle: keep it on direct journeys and label any transfer-journey action explicitly as tracking the first ride only, or omit that action there; never imply complete three-ride tracking.

## Acceptance

Synthetic fixtures cover directionality, repeated stop occurrences, permissions, exact two transfers, rejection of four vehicles, all walk totals/limits, different actual interchange coordinates, a useful sixth-or-later route, transfers even with three direct options, filter-before-limit, same point, disconnected network, invalid coordinates and failed network retry. Shared IDs and nearby distinct IDs work; crossing polylines with no associated stop do not. Metro reverse and branch directions use correct manual stops. Render both languages and all vehicle types, selection/relinking of third ride, generic map segments, unchanged multi-stop reorder/cancel behavior. Benchmark complete shipped network initialization and repeated queries, report timings and state counts; worker performs heavy work and caches index, without per-query network reload or unbounded all-to-all path enumeration. Pass existing tests and production build.
